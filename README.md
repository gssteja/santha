# Santha

A private, self-hosted Android app store — and a pipeline where you **add a new app just by
prompting Claude**. Claude writes the app, pushes it, GitHub Actions builds the APK, and it
appears in the store for you to install. One store APK is sideloaded onto a phone once; every
other app installs *through* it.

Live at `https://santha.t3ja.com` (behind Caddy + Let's Encrypt, password-protected).

---

## The idea: prompt → app in the store

You don't build or deploy by hand. The loop:

```
You (phone or laptop) ──prompt──> Claude Code (claude.ai/code, on the repo)
        │                               │ writes the app, commits, pushes a `<id>-vX` tag
        │                               ▼
        │                        GitHub Actions  ── builds signed APK ──> POST to the store
        ▼                               
Open Santha on your phone ──> new app is listed ──> tap Install
```

1. **Prompt Claude.** From the browser/mobile (claude.ai/code) connected to this repo, ask for an
   app — e.g. *"build a habit tracker and deploy it."*
2. **Claude scaffolds + ships it.** It creates an Expo app under `apps/<id>/`, adds a build
   workflow, commits, and pushes a release tag (`<id>-v1.0.0`).
3. **CI builds + publishes.** GitHub Actions builds a signed arm64 APK and `POST`s it to the
   server. No local Android toolchain involved — the build happens in CI, so even a phone-only
   prompt results in a real APK.
4. **Install from your phone.** Open Santha → the app appears → tap Install.

The web Claude sandbox doesn't compile APKs itself; it only edits + pushes. The heavy lifting
(Android SDK/NDK, signing) runs in GitHub Actions, which is why committing `android/` and the
workflows matters (below).

You can also trigger a build without Claude: the **Run workflow** button in the Actions tab, or
push a tag yourself.

## Repository layout

```
apps/
  santha/      The native store client (Expo / React Native, SDK 53, RN 0.79)
  <id>/        Each installable app — its own Expo project + android/ + deploy workflow
server/
  server.js    Express API + static web store (port 3000, fronted by Caddy)
  public/      Web store UI (index.html) + hosted apps (public/apps/<id>/app.apk + meta.json)
.github/workflows/
  <id>-deploy.yml   One per app: build a signed APK and publish it to the store
deploy.sh      Server bootstrap/deploy helper
```

Apps are **bare-workflow** RN: `apps/*/android/` is committed (not regenerated by
`expo prebuild`) so CI builds the exact native config. **Do not run `expo prebuild --clean`** —
it wipes the committed NDK / architecture / lint / signing setup.

## Architecture

```
phone (Santha app) ──> downloads APK from server, fires INSTALL_PACKAGE intent
browser ────────────> https://santha.t3ja.com  (web store, basic-auth)

                 santha.t3ja.com (Caddy, HTTPS 443)
                          │ reverse_proxy
                 Express server (127.0.0.1:3000, systemd `santha`)
                          │
                 public/apps/<id>/  (app.apk + meta.json)
```

- `GET /api/apps` lists apps from each `public/apps/<id>/meta.json`.
- APKs download via `/apps/<id>/download` (served with a friendly `<Name>-<version>.apk` name).
- `POST /api/apk/<id>` (deploy-key protected) is how CI publishes a new/updated app.
- Apps may be **APK** (installed) or **PWA** (opened in the browser).

## Auth model

Three tiers, least privilege in the client:

| Credential | Who holds it | Grants |
|---|---|---|
| **Caddy basic auth** (`santha` / password) | the browser (you) | web store + APK downloads + `/api/apps` |
| **App key** (`SANTHA_APP_KEY`) | baked into the apps | store reads (and any app↔server data); skips the basic-auth prompt |
| **Deploy key** (`SANTHA_API_KEY`) | CI only, never in an app | publish / delete apps |

Caddy gates the web/store/download paths with basic auth, *bypassed* when a request carries the
app key (so the native apps work without a prompt).

## Build & deploy

GitHub Actions does every build. **Trigger:** the Actions **Run workflow** button, or push a tag:

```bash
git tag <id>-v1.0.1 && git push origin <id>-v1.0.1   # builds + publishes that app @ 1.0.1
```

The tag suffix becomes the store version. Each app's workflow installs NDK 30 (accepting the
preview license), runs `generateCodegenArtifactsFromSchema` before `assembleRelease` (a fresh
`npm ci` lacks the per-library codegen JNI dirs), signs with that app's release keystore, and
`POST`s the APK to the server.

**Per-app secrets** (GitHub → Settings → Secrets): the shared `SANTHA_API_KEY` +
`EXPO_PUBLIC_STORE_KEY`, plus the app's `*_KEYSTORE_BASE64 / *_KEYSTORE_PASSWORD /
*_KEY_ALIAS / *_KEY_PASSWORD`.

### Local dev (optional)

```bash
cd apps/<id>
npm ci
npx expo run:android   # build debug + install to a running emulator + Metro
npx tsc --noEmit
```

A local `./gradlew assembleRelease` falls back to debug signing unless the `*_UPLOAD_*` gradle
props are passed — works with no keystore setup, but the output is debug-signed (different
signature than CI).

### Server

Express under systemd as `santha` (`/opt/santha/server`), behind Caddy. Reads `SANTHA_API_KEY`
and `SANTHA_APP_KEY` from `/opt/santha/.env`. Small server changes ship via
`scp server/server.js sachem:/opt/santha/server/server.js && ssh sachem 'systemctl restart santha'`.

## Design tradeoffs & known limitations

A personal, low-stakes project — choices favor "simple + good enough" over robust.

**The prompt-to-deploy loop**
- **Each new app still needs its own workflow + keystore + secrets.** Claude sets these up when it
  scaffolds the app, but there's no single generic/templated build job — so "just prompt it" hides
  real per-app setup (a keystore is generated, secrets are added) on the first deploy.
- **The web Claude sandbox can't compile APKs** (no Android SDK there). It only edits + pushes;
  CI does the build. If the workflow/secrets aren't right, a prompt-driven deploy fails in CI, not
  visibly to the prompter.
- **Builds cost CI minutes** (~6–8 min each, private-repo quota) and aren't instant.

**Store / distribution**
- **Sideload, manual installs.** Android won't let a sideloaded store silently install or update
  apps — every install needs a tap + the one-time "install unknown apps" grant. No background
  auto-update.
- **One-time uninstall on signature change.** Moving an app from an earlier debug-signed build to
  the CI release keystore requires uninstalling it once; after that, in-place updates are clean.
- **Santha can't truly self-update** — it offers its own APK as a download; updating the store
  means installing its APK by hand.

**Security**
- **The app key ships inside the APKs** and is extractable by anyone who decompiles one. It only
  grants store reads + app data (not deploy), and the APK itself sits behind download auth — so it
  blocks casual access, not a determined attacker. The deploy key is never in a client.
- **Single shared web password**, not per-user accounts: no revocation, audit, or multi-user.
- **Force-pushed history may linger** as bare SHAs in GitHub GC until collected (repo is private).

**Data / sync**
- Apps that sync (e.g. history) use **last-write-wins by id** — no real conflict resolution;
  concurrent multi-device edits can clobber. The server trusts what an authed client pushes.
- Server state is **flat JSON files**, no database, no backups beyond those files.

**Engineering**
- **No automated tests.** Verification is `tsc --noEmit` + manual emulator checks + curl probes.
- **Committed `android/` is hand-maintained** — the price of CI reliability is losing free
  `expo prebuild` re-runs; native changes are manual edits.
- **Mac → VPS uploads reset mid-transfer** (a host/network quirk), so large laptop pushes need an
  `rsync --partial --append` retry loop. CI (datacenter) avoids this — another reason deploys live
  server-side.
